ESP32 · LESSON 7

Talking to the Cloud: ESP32 + Blynk

Your ESP32 has been talking to the Serial Monitor and a local web page. Today it learns to talk to a phone from anywhere in the world — through a service called Blynk.

Before this lesson: students should be comfortable uploading a sketch, reading Serial.print() output, and using pinMode() / digitalWrite() / analogRead().
Part 1 · Concepts

What is Blynk, actually?

Blynk is a service that sits between your ESP32 and your phone. It gives you a mobile app and a website with drag-and-drop buttons, sliders, and gauges — so you don't have to build your own app to control your project.

  • Your ESP32 connects to the internet over Wi-Fi and reports in to Blynk's servers.
  • You build a control screen (a "dashboard") by dragging widgets onto it — no app-building required.
  • Tapping a button on your phone reaches your ESP32 in under a second, from anywhere with internet.
Why it matters: without a service like Blynk, "control my project from my phone" means writing a server, an app, and a way through your router's firewall. Blynk already built all of that.
Part 1 · Concepts

How the pieces talk to each other

Nothing connects directly to your phone. Everything passes through Blynk's cloud servers in the middle.

ESP32your hardware
⇄
Blynk Cloudthe middleman
⇄
Phone / Web Appyour dashboard
  • The ESP32 opens a connection to Blynk's servers and keeps it open — that's what Blynk.run() maintains.
  • When you tap a widget in the app, Blynk forwards that command to your ESP32 over the open connection.
  • When your ESP32 has new data, it pushes it to Blynk, and every open dashboard updates instantly.
Part 1 · Concepts

Five words you'll keep hearing

TemplateThe blueprint for your project type. It defines what data the device sends and receives. You build one Template, then create Devices from it.
DeviceOne physical ESP32, linked to a Template. Each Device gets its own Auth Token to identify it to the cloud.
DatastreamOne channel of data — like a labeled wire between your code and the dashboard. Each Datastream lives on a Virtual Pin.
Virtual PinNot a real pin on the board — a numbered slot (V0, V1, V2…) that carries one Datastream's value between your sketch and the app.
DashboardThe screen of widgets — buttons, sliders, gauges — that you drag and drop, each one wired to a Virtual Pin.

Setup 2 of 5

Create a Template

A Template is the blueprint. You only make one per project — every ESP32 running this lesson's code can be a Device under the same Template.

  1. Open the Templates page and create a new one.
  2. Name it something recognizable, like "E21 Blynk."This name is only for you — it never appears in your code.
  3. Set the hardware to ESP32.This tells Blynk which connection type and code examples to show you.
  4. Save the Template.You'll be dropped into the Template's Info page — leave it open, you'll add Datastreams next.
Setup 3 of 5

Configure the Datastreams

Inside your Template, open the Datastreams tab and create three — one per Virtual Pin this lesson uses.

PinNameTypeDirectionRange
V0LED ControlIntegerApp → Device0 / 1
V1UptimeIntegerDevice → App0 – 100000
V2Light LevelIntegerDevice → App0 – 4095
Required setting: for V0, set Min 0 / Max 1 — that's what makes it behave like an on/off switch instead of a free number.
Setup 4 of 5

Build the Dashboard

Switch to the Web Dashboard (or Mobile Dashboard) tab and drag on three widgets — each one gets wired to a Datastream you just created.

Button

Drag it on, open its settings, and attach it to Datastream V0. This is your on/off switch for the LED.

Value Display

Attach it to V1. It will show how many seconds the ESP32 has been running.

Gauge

Attach it to V2. It will show the live sensor reading as a dial.

Widgets only show what a Datastream carries — get the Datastream range right in the previous step and the widget behaves correctly automatically.
Setup 5 of 5

  1. Go to the Devices page and create a new one "from Template."This links a specific ESP32 to the blueprint you built.
  2. Pick your Template and give the Device a name.The name is just for your own reference in the Blynk console.
  3. Open the Device and copy three values: Template ID, Template Name, and Auth Token.These three values are what your sketch uses to prove it's this device — never share the Auth Token publicly.

Part 2 · Arduino IDE Setup

Wiring

Two components this lesson: an LED the app will control, and a light sensor (or potentiometer) the app will read from.

LED — output, pin 15

LED anode through a 220Ω resistor to GPIO15. LED cathode to GND.

Sensor — input, pin 34

LDR (or potentiometer wiper) forms a voltage divider into GPIO34. GPIO34 is input-only and analog-capable — a good fit for analogRead().

No sensor on hand? A potentiometer wired the same way works identically for this lesson — turning it stands in for changing light.

Activity 1 of 4 — Code

Read & send the sensor

Credentials, pins & functions
#define BLYNK_TEMPLATE_ID "TMPLxxxxxx"
#define BLYNK_TEMPLATE_NAME "E21 Blynk"
#define BLYNK_AUTH_TOKEN "YourAuthTokenHere"

#include <WiFi.h>
#include <WiFiClient.h>
#include <BlynkSimpleEsp32.h>

char auth[] = BLYNK_AUTH_TOKEN;
char ssid[] = "YourWiFiName";
char pass[] = "YourWiFiPassword";

const int ledPin = 15;
const int sensorPin = 34;
BlynkTimer timer;

BLYNK_WRITE(V0) {
  int pinValue = param.asInt();
  digitalWrite(ledPin, pinValue);
}

void sendSensorData() {
  int sensorValue = analogRead(sensorPin);
  Blynk.virtualWrite(V2, sensorValue);
}
setup() and loop()
void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);
  Blynk.begin(auth, ssid, pass);
  timer.setInterval(1000L, sendSensorData);
}

void loop() {
  Blynk.run();
  timer.run();
}
Activity 1 of 4

Read & send the sensor

Wire up the light sensor (or potentiometer) and push its reading up to the Gauge on V2 — on a timer, instead of a blocking delay.

What's new: sensorPin names GPIO34. analogRead() returns a number from 0 (no light / one end of the potentiometer) to 4095 (bright light / the other end). BlynkTimer timer schedules a function to run repeatedly without blocking — timer.setInterval(1000L, sendSensorData) calls sendSensorData() every 1000ms. Blynk.virtualWrite(V2, sensorValue) pushes the number to Virtual Pin V2, and timer.run() in the loop is what actually checks and fires the timer.
Debugging tip: if the Gauge doesn't move, add a quick Serial.println(sensorValue) inside sendSensorData() first — confirm the reading itself is changing before suspecting the Blynk connection.
Expected result: the Gauge widget on your dashboard updates once a second and tracks the sensor in real time, and the Button still switches the LED.
Activity 2 of 4 — Code

Let the sensor drive the LED

Credentials, pins & functions
#define BLYNK_TEMPLATE_ID "TMPLxxxxxx"
#define BLYNK_TEMPLATE_NAME "E21 Blynk"
#define BLYNK_AUTH_TOKEN "YourAuthTokenHere"

#include <WiFi.h>
#include <WiFiClient.h>
#include <BlynkSimpleEsp32.h>

char auth[] = BLYNK_AUTH_TOKEN;
char ssid[] = "YourWiFiName";
char pass[] = "YourWiFiPassword";

const int ledPin = 15;
const int sensorPin = 34;
const int threshold = 2000;
BlynkTimer timer;

void checkSensor() {
  int sensorValue = analogRead(sensorPin);
  Blynk.virtualWrite(V2, sensorValue);

  if (sensorValue < threshold) {
    digitalWrite(ledPin, HIGH);
  } else {
    digitalWrite(ledPin, LOW);
  }
}
setup() and loop()
void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);
  Blynk.begin(auth, ssid, pass);
  timer.setInterval(1000L, checkSensor);
}

void loop() {
  Blynk.run();
  timer.run();
}
Activity 2 of 4

Let the sensor drive the LED

A different sketch, on purpose: instead of a person tapping the Button, the ESP32 itself decides when the LED turns on, based on the sensor reading.

What's new: there's no BLYNK_WRITE(V0) here at all — the app isn't sending anything down. checkSensor() reads the sensor, reports it to the Gauge, then compares it to threshold and drives ledPin directly with plain digitalWrite().
Expected result: the LED switches on and off by itself as you cover/uncover the sensor (or turn the potentiometer) — no button tap required. The Gauge keeps updating as before.
Students: try a few different values for threshold and watch where the LED flips — this is a good moment to talk about why the Button (app → device) and this (sensor → device) are two different data directions.

Activity 3 of 4

Add an uptime counter

No sensor or LED needed for this one — a good quick win if a group finishes early, or a simple standalone example of the timer pattern on its own.

What's new: millis() returns milliseconds since the ESP32 booted; dividing by 1000 gives seconds. sendUptime() pushes that number to Virtual Pin V1 once a second via the same BlynkTimer pattern from Activity 1.
Expected result: the Value Display widget on V1 counts up steadily, showing how long the board has been running since its last reset.
Activity 4 of 4 — Code

Track the sensor's min & max

Pins & variables
const int sensorPin = 34;

int minReading = 4095;
int maxReading = 0;

void setup() {
  Serial.begin(115200);
}
loop()
void loop() {
  int sensorValue = analogRead(sensorPin);

  if (sensorValue < minReading) minReading = sensorValue;
  if (sensorValue > maxReading) maxReading = sensorValue;

  Serial.print("Now: ");
  Serial.print(sensorValue);
  Serial.print("  Min: ");
  Serial.print(minReading);
  Serial.print("  Max: ");
  Serial.println(maxReading);

  delay(300);
}
Activity 4 of 4

Track the sensor's min & max

No LED, no Blynk — pure sensor practice. The ESP32 remembers the lowest and highest reading it's seen since power-on, and reports all three numbers every loop.

What's new: minReading and maxReading are declared outside setup()/loop(), so they persist across loop calls instead of resetting each time. Each pass compares the new reading against them and updates whichever record it beats.
Expected result: the Serial Monitor prints a running "Now / Min / Max" line. Fully covering the sensor or shining a light on it (or turning the potentiometer to each extreme) should push the min or max further.
Students: physically test both extremes of your sensor so the min/max reflect real limits, not just resting-desk values — then compare numbers with a neighbor using a different sensor.

Put it all together

This sketch combines Activity 1's sensor Gauge, Activity 3's uptime counter, and last week's manual Button — Button (V0) is a full alternative to Activity 2's auto-threshold logic, not a combination of both.

Expected result: your dashboard shows a Button that switches the LED, a live sensor Gauge, and a running Uptime counter — all working over the internet, not a local network.
For groups that finish early: try merging in Activity 2's threshold logic as well, and talk through what should happen if the Button and the sensor "disagree" about whether the LED should be on.
Challenge

Push the dashboard further

Pick one or more. Build on top of the final phase's code — don't start over.

Second output

Wire a second LED to GPIO2, create a Datastream on V3, and add a second Button widget for it.

Automation alert

In the Blynk console, set up an Automation that sends a notification when the V2 reading drops below a threshold you choose.

Brightness slider

Replace the on/off Button with a Slider on V0, and use analogWrite() to fade the LED's brightness instead of switching it.

Working with a different sensor this semester instead of an LDR or potentiometer? Swap sensorPin and the reading logic — everything else in the sketch stays the same.
Optional stretch idea: a passcode/keypad gate — e.g. a Datastream that only unlocks the LED Button after the right code is entered. It's a bigger jump (needs a new widget and some state logic not covered above), so treat it as a "if there's time" extension rather than a core challenge.
